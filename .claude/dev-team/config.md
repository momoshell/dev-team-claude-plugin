## cmux_env_file

Opt-in, per-task workspace environment injection (ADR-018), available only under `execution_mode: cmux`. Two keys — `cmux_env_file: <absolute path>` and `env_file_keys: [KEY1, KEY2, ...]` — both read fresh from this file on every `workspace` invocation. **Write each as its own bare top-level line in the real config, never inside a fenced code block** (a fenced/indented example is deliberately ignored by the reader, exactly like `execution_mode:`'s own convention above) **and never more than one such line** (a second one makes the config ambiguous and `workspace` refuses).

- **`cmux_env_file`** — an absolute path to a plain `KEY=VALUE` env file. Absent (the default) reproduces today's behaviour exactly: no `--env-file` flag is ever emitted to `cmux new-workspace`, and no `env_file` block is ever written to `workspace.json`.
- **`env_file_keys`** — an explicit, closed allowlist (a single-line bracketed list) of every key the file may contain. This is the PRIMARY control: any key present in the file but absent from this list refuses the whole `workspace` call, naming the key. A key listed here but absent from the file only warns and proceeds. **Declaring a key here is a SECURITY assertion, not a lint** — non-reserved does NOT mean safe. Residual dangerous-but-unreserved families you may still be tempted to declare: `PAGER`/`EDITOR` (invoked interactively), `PYTHONPATH`/`PYTHONSTARTUP` (code injection into any Python the worker runs), `TMPDIR` (redirects where temp files land), `SSH_AUTH_SOCK` (redirects the SSH agent socket). Rule of thumb: if you can't say why a key is safe to inject into a worker's environment, don't declare it.
- **Non-overridable reserved-key backstop** — regardless of `env_file_keys`, a fixed set of keys (`PATH`, `NODE_OPTIONS`, `NODE_PATH`, `BASH_ENV`, `ENV`, `SHELL`, `IFS`, `HOME`, `XDG_CONFIG_HOME`, `ZDOTDIR`, `PROMPT_COMMAND`, `HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, `SSL_CERT_FILE`, `CURL_CA_BUNDLE`, `REQUESTS_CA_BUNDLE`, and every key starting with `ANTHROPIC_`, `CLAUDE_`, `DEVTEAM_`, `CMUX_`, `DYLD_`, `LD_`, `NODE_`, `GIT_`, or `npm_config_`, matched case-INSENSITIVELY — e.g. `NPM_CONFIG_SCRIPT_SHELL` is caught too, since npm itself honours that spelling) always refuses, even when declared. This backstop is deliberately incomplete — the closed allowlist above is what makes that acceptable (see `scripts/cmux/resolve.mjs`'s `ENV_FILE_RESERVED_EXACT`/`ENV_FILE_RESERVED_PREFIXES`).
- **Strict parser, refuse-never-repair** — only blank lines, `#` comments, and `KEY=VALUE` are accepted (a leading BOM is stripped, CRLF is normalized to LF). `export FOO=1`, any quoted value (double, single, or backtick), a trailing-backslash continuation, any character outside tab/printable-ASCII, a duplicate key, or any other malformed line refuses the ENTIRE file, naming only the 1-based line number — never the value or line content (env files carry secrets). The file itself must be an absolute path to a regular, readable file no larger than 64 KiB (a symlink is refused, never followed) — any violation refuses with the distinct `env_file_unreadable` reason.
- **Supplied only at workspace creation** — the env file is passed as a single `--env-file <path>` argument on the `new-workspace` call that creates the task's workspace (never per-dispatch, per-role, or per-pane, and never re-composed into `--env KEY=VALUE` flags). Once a workspace is created, its `env_file` block in `workspace.json` is stamped once and carried forward verbatim on every later `workspace` call against the same workspace — a later `workspace` invocation with a CHANGED, newly-added, or newly-removed `cmux_env_file` against an already-created workspace REFUSES loudly (naming the recorded and current paths/hashes) rather than silently doing nothing. **Remediation:** close the workspace (`cmux close-workspace`, or let `teardown` do it) and re-dispatch to apply the new environment.
