- **2026-08-05** — `spec-lint.mjs`'s bare-mention path regex had **three independent defects**, not one — corrects the mis-attribution in the (now-deprecated) 2026-08-02/08-03 entries above. (1) The negative lookbehind on all three path regexes omitted `-`, so a hyphenated absolute citation (e.g. inside `.../dev-team-claude-plugin/tasks/...`) re-matched mid-path. (2) The absolute-citation regex resolved its match against the **project root only**, never against the filesystem, so a real filesystem-absolute citation produced a phantom `<root>/Users/...` path. (3) **The actual "double-extension chopping" mechanism**: given `<dir>/<name>.test.mjs:425`, the bare-mention regex's end lookahead `(?![\w:])` rejects the full match because a colon follows, so the engine backtracks the base `[\w.-]+` quantifier all the way to the **earlier** dot (`name.test` + `.` + `mjs` failed → retry at `name` + `.` + `test`, where the next char `.` passes the lookahead) and reports a truncated, nonexistent path — while the real cited file exists and was already checked correctly by the citation-with-line-number pass. It fires only when a citation pass has already claimed that span; a bare mention with no line number never triggers it. Fixed by **span exclusion** (the citation passes record the character ranges they match; the bare pass skips any overlap), not by widening the lookahead — widening it to reject any trailing dot regresses the legitimate "bare mention at the end of a sentence" case. *Why:* two rounds of static analysis on this class were wrong before a live mechanical repro (running `spec-lint.mjs` against the planning spec's own `discovery_context`, which cited real files by name+line) surfaced the true trigger condition — see the paired qa-notes.md entry on requiring live reproduction, not static reading, before striking a claimed defect.
- **2026-08-05** — The `contract.mjs` throw-on-contract-error / return-on-instance-error pattern (2026-08-01 entry) now has data-file-loader precedent beyond schemas: `spec-lint.mjs`'s `loadSchema()`/`loadNoiseGlobs()` throw on **three** distinct failure modes, not just read/parse failure — unreadable, unparseable, **and well-formed-but-structurally-wrong** (e.g. a schema reduced to `{}`, or a noise-glob file whose `globs` key isn't a string array). The third case is the one worth remembering: `JSON.parse` succeeding is not proof the content is usable, and a defensive `try/catch -> []`-style degrade on any of the three silently turns a hard floor (A2's dispatch-refusal check; issue #9's noise-glob WARN) into no floor at all, with every existing "happy path" test still green. Assert the specific shape a loader's caller actually depends on (non-empty `required` array, `properties` as a plain object, `globs` as `string[]`) before memoizing — memoizing a bad value caches the defect for the process lifetime.
- **2026-08-05** — **`process.exit(main(...))` truncates large stdout when stdout is a pipe — use `process.exitCode = main(...)` instead for any CLI whose output can exceed ~64KB.** `process.exit()` tears the process down synchronously; `process.stdout` writes are asynchronous when the stream is a pipe (the normal case for a subprocess consumer, e.g. A2/B1/the orchestrator invoking `spec-lint.mjs --json`), so a large payload gets cut off mid-write at the OS pipe-buffer boundary (observed: exactly 65536 bytes) with no error — the consumer's `JSON.parse` just fails, or worse, gets a truncated-but-parseable prefix. `process.exitCode = <n>` sets the exit status without tearing anything down; the process still exits promptly once the event loop drains (no open handles survive synchronous `readFileSync`-based I/O). *Why:* `code-reviewer-deep` reproduced this on `spec-lint.mjs --json` with ~4000 diagnostics during A1's review — a Must-fix that a 178-test suite (all spawned with small fixtures) had no way to catch, since the bug is a payload-size threshold effect, not a logic error.
- **2026-08-05** — A hand-rolled `for (const x of spec.some_array_field)` check crashes or silently misbehaves if the field is actually a string, not an array — `for...of` over a string iterates its **characters**. Since the JSON-schema validation pass already reports the type violation for a non-array field, the hand-rolled check should `if (!Array.isArray(field)) return` (or `continue`) rather than iterate — otherwise a single bad-type mutation produces the correct schema FAIL plus N spurious per-character diagnostics from the hand-rolled pass, breaking any "exactly one diagnostic per mutation" test convention. Applies wherever a hand-rolled check runs in parallel with schema validation on the same field (`spec-lint.mjs`'s `checkFilesInScope`/`checkValidationCommands`, A1).
- **2026-08-05** — A CLI-as-library refactor (top-level `parseArgs`/read/checks/`process.exit` → an importable function) needs its **usage/parse-error path** to throw a tagged error class (e.g. `class UsageError extends Error {}`) rather than call `process.exit` directly from a helper — otherwise the library entry point (`main(argv) -> number`) can still tear down the caller's whole process on a bad argument, even though the promised contract is "return an exit code." `main`'s own `try/catch` maps `UsageError` to its usage exit code and anything else to a different one; only the top-level CLI-invocation guard (`invokedDirectly`) sets `process.exitCode` from the return value and lets the process exit normally. Precedent for future top-level-side-effect scripts being libraryized the same way (`spec-lint.mjs`, A1).
