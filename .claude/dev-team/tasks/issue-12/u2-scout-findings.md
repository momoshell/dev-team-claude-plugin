# U2 live scout findings — cmux 0.64.22, run 2026-08-06 by the orchestrator

Resolves the architecture package's A1–A4 assumptions plus two new findings. All firsthand.

- **A1 VERIFIED.** `cmux browser open http://example.com --workspace <UUID> --focus false` → `OK surface=surface:9 pane=pane:7 placement=…`. UUID accepted.
- **A2 CORRECTED.** `--load-state load` is INVALID — the CLI's accepted literals are `interactive|complete` (per `cmux browser --help`), and `load` produced `Error: js_error: Wait condition could not be evaluated: Timed out waiting for the browser document to become ready`. **`--load-state complete` verified working** (returned OK ~instantly on a loaded page). IC-2's `browserWaitLoad` must emit `complete`.
- **A3 FAILED, both halves that matter.** `cmux rename-tab --surface <browser-uuid> "dev-team preview"` → `Error: not_found: Tab not found` (tried on two different browser surfaces; the same verb works on terminal surfaces in production `dispatchCmd`). And the browser surface's `title` field in `tree --json` **tracks the page hostname** (`example.com`), i.e. it is dynamic and navigation-controlled. The frozen-title fallback (`PREVIEW_TAB_TITLE`) is unimplementable on 0.64.22 — D4's "designed to be safe if false" arm is now the actual design: **record-only singleton**. The adopt arm needs a replacement decision (note: tree surfaces do carry `title` = hostname, and rung-2 doc tabs carry `file://`-derived titles, so a coarse http(s)-vs-file discrimination exists if wanted — but it is page-controlled text; treating it as anything more than a heuristic would violate the package's own byte-discipline).
- **A4 VERIFIED, with a caveat.** `screenshot --out <arbitrary abs path>` works. **Caveat: on a surface whose document never became ready, it still returned `OK` and wrote a full-size (2560×1440, 68KB) pure-white PNG.** Screenshot success ≠ evidence of render; `existsSync` cannot detect blankness. The gate-report line should not imply the screenshot proves a rendered app.
- **NEW — stacked browser surfaces are undrivable (the singleton is operational, not hygiene).** With TWO browser surfaces stacked in one pane (the `placement=reuse` behavior), `errors list` and `wait` on EITHER surface failed with `Error: js_error: Timed out waiting for the browser document to become ready`, and the screenshot came back blank — while the identical single-surface flow in an equally unfocused workspace loads, waits, reports errors, and screenshots correctly (verified both ways, same session). A second stacked surface doesn't just clutter: it can render the preview undrivable at the gate. This materially strengthens D4's fail-closed-on-ambiguity arm.
- **NEW — `js_error` is a distinct error code shape.** Browser sub-verb failures arrive as `Error: js_error: <detail>` on stderr with exit 1 — parseable by cmuxctl's existing `/^Error:\s*([^:]+):\s*(.+)$/m` as `{code:'js_error', …}`. Wrappers should expect it.
- **Re-verified:** unfocused workspaces load pages fine (single surface); `errors list` clean literal `No browser errors`; positional refs renumbered mid-probe (`close-surface --surface surface:8` → `not_found` after later topology changes) — a good fake-cmux behavior to keep in mind.

## Addendum — timing probe, 2026-08-07 (orchestrator, live 0.64.22)

- **`browser open <url>` is fire-and-forget:** returns `OK surface=… placement=split` in **0.06s** even when nothing listens at the URL — it does not wait for the load. Lock-hold time under `withRecordLock` is therefore bounded by the open call itself, far under `LOCK_STALE_MS` (30s).
- **`goto` on a dead port self-bounds at ~15.5s** with a NEW error code: `Error: navigation_timeout: Timed out waiting for the browser document to become ready` (distinct from `js_error`). Spawn `timeoutMs` for `browserGoto` must exceed ~15s (e.g. 20s); `browserWaitReady` spawn must exceed its own cmux-side `--timeout-ms`.
- **A failed navigation leaves the console CLEAN** — `errors list` on the dead-port surface returns `No browser errors` in 0.04s (connection-refused is not a console error). "clean (0)" on a never-loaded page is therefore reachable; ONLY `load_state_confirmed: false` prevents the vacuous claim — confirms the v1.1 suppression design is load-bearing, not belt-and-braces.
- Error-code vocabulary observed across probes: `js_error`, `navigation_timeout`, `not_found`, plus the documented `invalid_params`/`invalid_state`/`not_supported`. Code-only logging (backend consult §2-2) handles all uniformly.
