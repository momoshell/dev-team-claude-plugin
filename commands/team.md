Interpret `$ARGUMENTS`:

- **a request, or empty** → engage the team for this request now, skipping the semi-auto suggestion. Classify it; for Tier 3, have `dev-team:architecture-lead` produce the artifact-routed architecture package (PRD-lite/TRD/ADR only as needed) and `dev-team:plan-reviewer` review it before approval; consult the relevant `dev-team:*-lead`(s) for Handover Spec(s) (format: `${CLAUDE_PLUGIN_ROOT}/handover-spec.md`), lint each with `scripts/spec-lint.mjs` before dispatch, dispatch `dev-team:coder`(s), run the risk-sized QA gate per `${CLAUDE_PLUGIN_ROOT}/references/qa-gate.md` (`dev-team:qa-lead` plans it; the reviewer tier + `build-validator`/`test-engineer` are added only as the risk ladder warrants — not an unconditional bundle), then commit reconciled memory deltas.
- **`off`** → for the rest of this session, stay direct: don't propose or engage the team unless `/dev-team:team` is invoked again.
- **`auto`** → for the rest of this session, run qualifying (Tier 2/3) work through the team automatically, without the semi-auto confirmation.
- **`status`** → report the current activation mode and the available leads.
- **`mode cmux|agent-tool`** → write `execution_mode: <value>` to `.claude/dev-team/config.md`, as a bare top-level line on its own (never inside a fenced code block); the only accepted values are `cmux` and `agent-tool`; if an `execution_mode:` line already exists, REPLACE it — never add a second, because a config with more than one `execution_mode:` line is refused as ambiguous and every mutating dispatcher verb then fails; `mode` with no argument reports the current value (absent key = `agent-tool`); `cmux` opts this repo into the pane dispatcher (protocol in `references/cmux-dispatch.md`), `agent-tool` is the default Agent-tool substrate.
- **`roster <role>=<agent>:<model>`** → a **session-scoped** override of one existing roster role for the rest of this conversation — it lives only in this session, is never written to `config.md`, and does not survive `/clear`. Delivered to `dispatch.mjs` as the `session` key of the `--config <path>` JSON sidecar, e.g. `{ "session": { "roles": { "coder": { "agent": "claude", "model": "opus" } } } }`, deep-merged over the plugin default / `~/.claude/dev-team/roster.json` / project `.claude/dev-team/roster.json` layers (arrays replace wholesale, never concatenate). It **overrides an existing role, it never creates one** — refuses if `<role>` isn't already a role in the resolved roster (a fragment for an unknown role produces a role object missing required schema keys and the merge throws). Refuses if `<agent>` isn't a supported agent CLI — the schema's `agent` enum makes the merge invalid, and any task with no `roster.snapshot.json` yet throws on dispatch (an already-dispatched task falls back to its frozen snapshot instead — see below). `<model>` has no equivalent merge-time check: the schema only requires a non-empty string, so a bogus `<model>` — from this verb or hand-authored into either persistent layer below — merges silently and reaches the dispatcher CLI unchecked; only `test/roster.test.mjs` checks `MODEL_ALIASES` coverage, and only against the shipped default, never a merged roster. To make an override stick, don't use this verb — edit one of the two persistent roster layers instead: `~/.claude/dev-team/roster.json` (personal, applies across all your projects) or `<project>/.claude/dev-team/roster.json` (project-scoped, higher-precedence than the personal one, and committed by default — git-exclude it locally via `.git/info/exclude` if you want it personal instead — only effective before the file is first committed; after that, `git rm --cached` it too). There is no persisted session layer and none is planned — but an override already in flight is different: `dispatch.mjs` freezes the merged roster (override included) into that task's `roster.snapshot.json` at first dispatch, so an already-dispatched task keeps the override through `/clear`; only a new dispatch reverts to whatever the persistent layers resolve to. Either file may be a partial fragment, since only the merged roster is validated, e.g. `{ "roles": { "coder": { "model": "opus" } } }`.
- **`workflow <goal>`** → for large or repeatable jobs, run the deterministic pipeline via the Workflow tool with `scriptPath: ${CLAUDE_PLUGIN_ROOT}/team-build.workflow.mjs`, passing `{ goal, projectMemory, tasks: [{ id?, domain, brief, files?: string[], depends_on?: string[] }] }` as `args`. Leads → executor (coder, or test-engineer for `qa`) → gate (review tier per the ladder + build-validator), with one amend-retry on `insufficient`. Plan-domains: **frontend/backend/devops/qa** — unroutable domains (e.g. `mobile`, or `architecture` = interactive Tier-3) are rejected, not laundered (returned in `rejectedTasks`). Set `depends_on` (task `id`s) for ordered work — the workflow runs tasks in dependency waves and skips a task if any dependency fails its gate (cycles/unknown deps are skipped with a reason). Before planning a dependent task, the workflow auto-injects its finished prerequisites' `interface_contract` + changed files into the lead's prompt, so a dependent spec stays coherent with what upstream actually shipped without you brokering it by hand. Note the workflow can't run spec-lint mid-script — it relies on the schema's field-presence check + one amend-retry, and it auto-escalates every `devops` task to deep review. **Workflow mode always stays on the Workflow tool's own `agent()` dispatch** — cmux panes apply to conversational dispatch only, never to workflow-mode execution.
