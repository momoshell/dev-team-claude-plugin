# Plan review — architecture-package-v1 (deterministic backbone)

**Reviewer:** dev-team:plan-reviewer · **Date:** 2026-08-04 · **Verdict: revise**

> revise — the package is unusually strong on the architecture questions (§3, §5, §7 are sound), but it ships a Phase A that collides with an open epic issue on the same file, mechanizes a linter whose known-good behavior it hasn't verified against the pane environment, misses two brain-file deviations that need ratification, and its own load-bearing constraint (§2.1, no long-blocking segment) is violated by the B8 `ship` segment it plans.

## Must Fix

**1. §12 / A1 — A1 and epic issue #9 both rewrite `scripts/spec-lint.mjs`, and A1 is scheduled parallel with #9.**
A1's dependency line reads *"Depends on: nothing. Parallel with #7 / #8 / #9 — touches no cmux surface."* But #9's scope includes *"spec-lint WARN never FAIL"* — #9 edits `spec-lint.mjs`. A1 restructures the entire file (module-level `parseArgs`/`checkFields`/`process.exit` at `:202-212` moved into `main()`, `failures`/`warnings` at `:33-34` moved into a closure). Whichever lands second gets a whole-file conflict, and the more likely outcome is that #9's WARN-downgrade silently lands on the pre-refactor structure and is lost or re-implemented. The author caught the analogous A2/#7 collision; the same reasoning was not applied to A1. Fix direction: A1 depends on #9 (or #9 is absorbed into A1), not parallel with it.

**2. §12 / A2 + §15/U4 — A2 makes `spec-lint` a hard dispatch refusal *before* the environment-parity unknown it depends on is scouted.**
`spec-lint.mjs:198` fails a spec when `checkValidationCommands` cannot find the command's binary on `process.env.PATH` — the *parent's* PATH. A2 puts that check inside `dispatchCmd` as a refusal (exit 1, zero panes spawned). U4 is flagged as unverified and assigned a scout **before B1**, i.e. Phase B. But A2 is Phase A. Failure scenario: a project whose `validation_commands` use a tool present in the pane's shell profile but absent from the orchestrator's Bash PATH — every coder dispatch for that project is now structurally unspawnable, with no override, in a contract-freeze-set file. Fix direction: Scout 2 (U4) gates A2, not B1; or A2's refusal covers only the field/path checks and treats `validation_commands` PATH failures as non-blocking.

**3. §12 / A2 + §8.3 seq 2 — `checkFileLineRef` FAILs on stale line citations, and the chain has no bound on the `spec_gate` amend loop.**
`spec-lint.mjs:118` FAILs when a cited `file:line` exceeds the file's current line count. In B7's Tier-3 per-phase sub-chains, specs are transcribed at plan time and dispatched phases later — after earlier phases have changed those files. So a spec that passed lint at transcription time hard-FAILs at dispatch. §8.3 segment 2 then halts `amend`, but §4.2's "the chain owns zero retry counters" means nothing bounds this: there is no *existing brain bound* for spec-gate bounces to count (the ≤2 bound at `orchestration.md:53` is for coder `insufficient`, a different loop). Halt → orchestrator re-transcribes → halt is an unbounded turn-burner, which directly attacks the §14 risk-1 thesis. Fix direction: either a stated bound (which is a new bound and therefore a ratification item) or an explicit "spec_gate FAIL after N is an `escalation` halt" rule; and A1 should make line-drift a WARN, not a FAIL, given A2 turns it into a refusal.

**4. §13 — two brain-file deviations are missing from the ratification list.**
- **`orchestration.md:58` is not listed.** §13.1 asks to amend `qa-gate.md:7`, but the *same* invariant is stated in the brain file itself: `orchestration.md:58` — *"deterministic validation runs inline, not as a window — you re-run the spec's scoped `validation_commands` yourself via Bash."* One of "Three invariants regardless of tier." A chain that runs validation on the orchestrator's behalf contradicts `orchestration.md` directly, and only the reference file was flagged. Must be a named ratification item alongside §13.1.
- **A1's behavioral changes to spec-lint are not listed.** Binding constraint (1) is "BRAIN UNCHANGED — no change to tier semantics, **spec-lint**, QA-gate ladder, memory protocol, ship flow" — one existing exception (D16 spec-lint WARN) exists *because* changing spec-lint's FAIL/WARN classification needed an exception. A1 scope item 4 downgrades `discovery_context`'s missing-file hard-FAIL to a WARN, and item 3 changes the path regexes so specs that FAIL today PASS tomorrow. §13.5 flags only *A2*; A1's change to what spec-lint *means* is unflagged and is a fourth spec-lint exception. Add as §13.8.

**5. §12 / B8 + §2.1 — the `ship` segment violates the package's own most load-bearing constraint, and U2 is scoped to the wrong slice.**
§2.1: *a chain segment cannot be one long-blocking subprocess.* Resumability handles **outstanding dispatches**; it has no mechanism for a long-running **local** command. B8's `ship` segment runs `config.validate.full`, which `qa-gate.md:7` describes as running "for tens of minutes." `evidence.mjs`'s runner is synchronous inside a `chain step`. The one place the chain is guaranteed to blow the Bash tool timeout is B8, and U2 is scoped as "needs a measurement before B4" — B8 is not named. Fix direction: either the step machine gains a `still-running` state for local commands (a real interface addition), or B8 explicitly leaves `validate.full` orchestrator-owned and the `ship` segment covers teardown only.

**6. §5.3 / ADR-016 — mapping a self-contradictory verdict onto `inconclusive` is a semantic widening of a brain rule, claimed as "zero brain change," and prescribes a remedy that doesn't fit.**
`qa-gate.md:33` and D17 define `inconclusive` by *absence* ("no verdict"). `verdict_consistent` produces `inconclusive` for a verdict that is present, parseable, enum-valid but contradicts its own `findings[]`. (a) The orchestrator reading `qa-gate.md` has no rule covering this input, so "zero new branch" is only true if the orchestrator never notices; (b) "re-run scoped to the diff" is the wrong remedy for `verdict:"pass"` alongside a `severity:"critical"` finding — the critical finding is *already* a block per `qa-gate.md:29`, and re-running the same reviewer likely reproduces the contradiction, burning a window. Fix direction: either accept as a fourth exception and write the branch, or route contradiction to `changes-needed` (the critical finding is the evidence), not `inconclusive`.

**7. §12 / B9 + §2.6 — "substrate-neutral wording" in `next.md`/`ship.md` satisfies the test but not the invariant.**
The guard's stated purpose (test header `:595-601`) is that every command other than `team.md` stays **substrate-agnostic**. The chain has no Agent-tool backend and requires cmux preflight. Wiring `next.md`/`ship.md` to invoke the chain makes them substrate-*dependent* while passing the regex — defeated by synonym. Failure scenario: a user on `execution_mode: agent-tool` runs `/dev-team:next`, which now drives a runner that cannot start. Fix direction: B9 wires only `orchestration.md`/`team.md` (the exempt surfaces), or the chain-invocation line is conditioned on execution mode — and that condition itself needs the guard's rationale re-argued.

## Should Fix

- **§6.2 / ADR-019 duplicates a frozen constant.** `contract.mjs:31` already exports `PROTECTED_PATH_COMPONENTS = ['.claude', '.git', '.vscode', '.idea', '.husky', '.devcontainer']`. ADR-019 defines a second, differently-shaped protected set with no reconciliation; the existing constant already covers all of `.claude/**` while `scripts/cmux/**` and `hooks/**` are genuinely new. Two protected lists is the same single-authority failure the package refuses for envelopes. Name one as authoritative or state the layering.
- **§12 / A1 — `--json` output channel unspecified.** Today FAIL/WARN lines + summary go to stdout. Pin it: `--json` ⇒ JSON to stdout, human lines to stderr, matching `dispatch.mjs:19-21`.
- **§8.3 seq 2 vs §12/A2 — the spec-lint gate exists in two places.** State which is enforcement and which is early-warning, or drop `spec_gate` once A2 lands.
- **§14 risk 1 — acceptance criterion not measurable as written.** No turn-counting method, no named baseline task, no tolerance; Scout 1 yields one number for one historical task on the old path. Realistic uncovered path: the chain converts one prose step into a halt→resolve→step triple (three tool calls where prose spent ~two); Tier-2 has four segments each with ≥1 halt plus spec_gate bounces. Define the metric as tool-calls-per-completed-slice, pick two paired tasks, state a tolerance.
- **§15 / U5 understated.** The initiative's central bet ("orchestrator calls `chain step` in a loop rather than narrating") is carried by ≤2 lines of orchestration.md headroom, with an unmeasurable mitigation. Promote U5 to a decision item alongside D-a/D-b/D-c.
- **§10 invariant 13 — `green_suite_fresh` needs a home.** `revised` is only meaningful if every mutation path sets it — including orchestrator out-of-band fixes and coder in-worktree edits after a green run. B6 owns the gate; nothing owns the flag's write points. Name them.
- **§15 / U8** should be resolved before B7 is *specified*, not at #8 planning — B7's design is structurally different if plan-reviewer gains a verdict block.
